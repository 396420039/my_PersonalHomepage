> 本文整理自 Anthropic 关于长时间运行编码 Agent 的工程实验。

复杂项目可能持续数小时甚至数天，但每个上下文窗口都是一次有限班次。仅靠自动压缩并不够：Agent 可能一次做太多，留下半成品；也可能看到已有成果后过早宣布完成。

```mermaid
flowchart LR
    I["初始化 Agent"] --> F["生成完整功能清单"]
    F --> G["建立 Git 与进度文件"]
    G --> C1["编码班次 1"]
    C1 --> H1["测试、提交、写交接"]
    H1 --> C2["编码班次 2"]
    C2 --> H2["测试、提交、写交接"]
    H2 --> N["后续班次直到验收"]
```

## 第一轮负责搭工作台

初始化 Agent 不急着完成所有功能，而是把模糊目标展开成可验证的功能列表，建立运行脚本、进度文件和初始版本。每项功能先标记为未通过，后续 Agent 才不会把“页面能打开”误判为项目完成。

## 每一轮只完成可收尾的增量

新的编码 Agent 先读取功能清单、进度记录和 Git 历史，再选择一个高优先级功能。结束前必须运行测试、修复明显问题、提交代码，并留下下一轮能快速理解的说明。

关键原则是保持环境处于可合并状态。上下文即将耗尽时，不应开启一个无法收尾的大改动。小而完整的提交，比宏大但中断的实现更能稳定累积成果。

## 外部状态比聊天记忆可靠

功能清单描述“还差什么”，进度文件描述“刚刚做了什么”，版本历史描述“代码如何变化”。三者共同形成可审计的长期记忆，也方便人类随时接管。

这种 harness 的本质并不神秘，它只是把成熟工程团队的交接习惯编码进 Agent 运行环境。
